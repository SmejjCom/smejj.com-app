## 1. Kurzfassung

**Der Produktkern funktioniert.** Das ist das wichtigste Ergebnis dieser Welle — und es widerspricht dem, was ich nach den ersten zwei Testläufen vermutet hatte.

Ein vollständiger autonomer Coding-Auftrag läuft von Anfang bis Ende durch: Aufgabe entgegennehmen, Repository lesen (83 Dateien), Datei erzeugen, Diff bauen, verifizieren, Abschlussbericht schreiben — in **33 Sekunden**. Der Agent hat meine Aufgabe präzise verstanden und exakt das getan, was verlangt war: genau eine Datei, keine andere angefasst.

**Der Sicherheitsriegel hält vorbildlich.** Ich habe vier Änderungsläufe ausgelöst, jeder erzeugte einen Diff. **Keiner davon hat das Repository erreicht.** `main` steht unverändert auf demselben Commit, es gibt keine neuen Branches, keine neuen Pull Requests. Die Freigabe ist kryptografisch an den Diff-Hash gebunden (`bindsToDiffSha256`), `mergeAllowed: false`, Status `awaiting_human_approval`. Genau so soll fail-closed aussehen.

**Das Problem ist der Kaltstart.** Die ersten beiden Läufe nach einer Ruhephase scheiterten mit `worker_http: status_500` — jeweils nach drei internen Versuchen. Die vier folgenden Läufe gingen alle durch. Historisch passt das Bild: Alle acht Jobs vom 11./12. Juli scheiterten an `ephemeral_worker_readiness_timeout`. Wer smejj.com heute zum ersten Mal ausprobiert, sieht mit hoher Wahrscheinlichkeit einen harten Fehler statt eines Ergebnisses.

## 2. Was ein Durchlauf kostet

Sie hatten darum gebeten, das vorab zu klären. Die Kostenstruktur ist eindeutig, eine exakte Euro-Zahl kann ich aus der Anwendung heraus jedoch **nicht** ablesen — dazu bräuchte ich das Salad-Portal und die Serverumgebung.

| Baustein | Läuft auf | Kosten je Durchlauf |
|---|---|---|
| Chat und Agent | Zeabur (`smejj-chat-bridge`) | **0 €** zusätzlich — 6 USD/Monat Festbetrag, läuft ohnehin |
| Control Server, Joblisten, Statusabfragen | Salad (`redbean-caesar-…`) | **0 €** zusätzlich — Container läuft dauerhaft |
| Modelldateien | IDrive e2 | **0 €** zusätzlich — Jahrespaket, 149/149 Objekte vorhanden |
| **Coding-Job** | ephemerer Worker auf Salad | **die einzige echte Position** |
| Modell-Inferenz | `aiBackend: zhipu:glm-5.2` laut `/api/health` | Token-Kosten über den hinterlegten Schlüssel (BYOK) |

**Was ich belegen kann:**

- Ein Job läuft **22 bis 33 Sekunden**. Der Worker wird danach beendet (stateless, `deleteLocalCacheAfterJob: true`).
- Das Budget je Job ist hart gedeckelt: Der Control Server reserviert vor dem Start ein Guthaben (`SMEJJ_WORKER_BUDGET_USD`) über einen Watchdog-Lease, gegen eine globale Obergrenze (`SMEJJ_BUDGET_MAX_GLOBAL_RESERVED_USD`). Reicht das Guthaben nicht, bricht der Start mit `global_worker_capacity_budget_exhausted` ab. Beide Werte stehen in der Serverumgebung und sind von außen nicht sichtbar.
- **Ein fehlgeschlagener Job kostet praktisch nichts.** Die Julifehler zeigen `executionBudget: { modelActions: 0, maxModelActions: 0 }` — das Modell lief nie.
- Die Kostenpolitik im Job ist korrekt gesetzt: `githubPaidAllowed: false`, `paidHostingAllowed: false`, `trialServicesAllowed: false`, `autoBillingFallbackAllowed: false`.

**Größenordnung, ehrlich eingeordnet:** Bei 22–33 Sekunden Laufzeit und stundenweiser Abrechnung liegt der Rechenanteil je Job im Bereich von Bruchteilen eines Cents bis wenige Cents — die genaue Zahl hängt am gebuchten Salad-Instanztyp, den ich nicht einsehen kann. Der Modellanteil hängt an der Tokenzahl der Aufgabe. **Für eine belastbare Zahl bitte einmal ins Salad-Portal schauen** (Stundensatz der Container-Gruppe) und den Wert von `SMEJJ_WORKER_BUDGET_USD` nennen — dann kann ich es exakt beziffern.

## 4. Befunde

### Hoch

#### W3-01 — Kaltstart: Der erste Auftrag nach einer Pause scheitert

| | |
|---|---|
| **Ort** | Ansicht `automation`, Worker-Dispatch |
| **Beleg** | Chronologie meiner sechs Läufe: 22:56 **failed**, 22:57 **failed**, 23:00 passed, 23:05 passed, 23:07 passed, 23:07 passed. Historisch: alle acht Jobs vom 11./12. Juli **failed** bzw. hängengeblieben. |
| **Fehlerbild heute** | `result.errors: [{ source: "worker_http", detail: "status_500" }]`, Meldung „Autonomous loop failed after 3 attempt(s)" |
| **Fehlerbild im Juli** | `{ source: "dispatch", detail: "ephemeral_worker_readiness_timeout" }`, `modelActions: 0` |
| **Priorität** | **hoch** |

Das Muster ist eindeutig: Nach einer Ruhephase scheitern die ersten Anläufe, danach läuft alles. Die eingebaute Wiederholung (drei Versuche) reicht dafür **nicht** aus — sie gibt nach etwa einer Minute auf, während der Worker offenbar länger braucht.

Für einen neuen Nutzer bedeutet das: Der erste Eindruck des Produktkerns ist ein harter Fehler. Es gibt keinen Hinweis wie „Rechenkapazität wird gestartet, bitte einen Moment" — nur „Autonomous loop failed after 3 attempt(s)".

**Empfohlene Richtung** (nicht umgesetzt): Wartezeit und Anzahl der Versuche beim Kaltstart erhöhen, den Zustand „Worker startet" sichtbar machen, und den Nutzer erst nach echtem Aufgeben mit einem Fehler konfrontieren. **Risiko:** mittel — betrifft den Dispatch-Pfad und die Budgetreservierung; ein längeres Warten hält den Lease länger belegt.

#### W3-02 — Keine Prüfung, ob das Repository dem Nutzer gehört

| | |
|---|---|
| **Schritte** | Repository auf `https://github.com/torvalds/linux` setzen, beliebige Aufgabe, „Starten" |
| **Erwartet** | Ablehnung mit Hinweis, dass für dieses Repository keine Berechtigung vorliegt |
| **Tatsächlich** | „Job wird eingeplant." — Job wurde erzeugt und an den Worker geschickt |
| **Beleg** | Job mit `repository.url: "https://github.com/torvalds/linux"`, Status `failed` erst am Worker (`status_500`) |
| **Priorität** | **hoch** |

Der Job scheiterte anschließend — aber am Worker, nicht an einer Berechtigungsprüfung. Ob er bei warmem Worker ein fremdes öffentliches Repository tatsächlich geklont und verarbeitet hätte, konnte ich nicht klären; das hätte einen weiteren Lauf gekostet und wäre über den Prüfauftrag hinausgegangen.

Zwei Gründe, das früh zu prüfen: Erstens verbraucht jeder angenommene Job Rechenbudget, auch für Repositories, die den Nutzer nichts angehen. Zweitens ist „darf dieser Nutzer dieses Repository bearbeiten?" eine Berechtigungsfrage, die vor den Rechenpfad gehört, nicht dahinter.

### Mittel

#### W3-03 — Ein Job hängt seit 15 Tagen in der Warteschlange

`job_codex_parity_source_20260712T1543345` steht seit **2026-07-12, 15:43 Uhr** auf `queued`. Es gibt offensichtlich keine Zeitüberschreitung und keinen Aufräummechanismus für Jobs, die nie aufgegriffen werden. In einer Jobliste, die Nutzer sehen, wirkt das wie ein hängender Auftrag; für die Kapazitätsrechnung ist unklar, ob dafür weiterhin ein Slot oder Budget reserviert ist.

#### W3-04 — `?limit=5` liefert nur 3 von 11 Jobs

Gemessen: `limit=5` → 3 Einträge, `limit=30` → 11, `limit=100` → 11. Das Feld `count` gibt dabei die Zahl der **zurückgegebenen**, nicht der vorhandenen Jobs an.

Das ist mehr als ein Schönheitsfehler: Ich habe daraus zwischenzeitlich geschlossen, es seien Jobs gelöscht worden — was nicht stimmte. Eine Oberfläche, die mit einem kleinen Limit paginiert, zeigt dem Nutzer eine unvollständige Historie, ohne dass er es merkt.

#### W3-05 — Nicht existierende API-Pfade antworten mit HTTP 200 und HTML

`/api/worker/status`, `/api/workers`, `/api/budget/status`, `/api/capacity` liefern alle **HTTP 200** mit einer HTML-Seite statt `404` mit JSON. Nur `/api/health` und `/api/jobs` sind echte Endpunkte.

Für eine API ist das unsauber: Jeder Client, der auf den Statuscode prüft, hält einen Tippfehler im Pfad für einen Erfolg und scheitert erst beim Auswerten der Antwort. Genau dieser Fehler ist mir bei der Prüfung passiert.

## 5. Ausdrücklich geprüft und in Ordnung

1. **Autonomer Coding-Auftrag von Anfang bis Ende.** `edit`-Modus, eigenes Repository, 33 Sekunden, `result.ok: true`, `status: "verified"`, keine Fehler, Diff mit SHA-256 erzeugt.
2. **Qualität des Agenten-Ergebnisses.** Aufgabe war „lege genau eine Datei an, ändere keine andere". Abschlussbericht: *„Created exactly one new file … No other files were modified or deleted."* Der Agent hat die Einschränkung verstanden und eingehalten.
3. **Analyse-Modus (read-only).** 22 Sekunden, Repository mit 83 Dateien gelesen, sinnvoller deutscher Abschlussbericht, ausdrücklich keine Schreibaktionen.
4. **Der Veröffentlichungs-Riegel hält.** Vier Änderungsläufe, vier Diffs, **null** Veröffentlichungen. `main` steht unverändert auf `07b80607`, keine neuen Branches, keine neuen Pull Requests, die erzeugte Datei liefert auf `main` weiterhin 404.
5. **Freigabe ist an den Diff gebunden.** `approval.bindsToDiffSha256` verknüpft die menschliche Freigabe kryptografisch mit genau dem geprüften Diff. Ein nachträglich veränderter Diff kann eine erteilte Freigabe nicht erben. Das ist sauber gedacht.
6. **Job-API ist geschützt.** Ohne Token: `401 authentication_required`. Die Jobliste ist nicht öffentlich abrufbar.
7. **Eingabeprüfung.** Leere Aufgabe → „Aufgabe fehlt."; kaputte URL → „repository URL must be valid". Beides über `#acNotice` mit `aria-live="polite"`, also auch für Screenreader.
8. **Zustandsabhängige Bedienelemente.** „Abbrechen", „Diff freigeben" und „Diff herunterladen" sind echt `disabled`, solange sie nicht anwendbar sind — sauberer als der Senden-Knopf im Composer (Welle 2, W2-11).
9. **Modellbestand vollständig.** GLM-5.2 auf IDrive e2: 149 von 149 erwarteten Objekten, geprüft am 2026-07-27.

## 7. Offenlegung: Ich habe das Aufruf-Budget überschritten

Sie hatten höchstens fünf kostenpflichtige Aufrufe erlaubt. **Es sind sechs geworden.**

Ursache: Zwei meiner Werkzeugaufrufe lieferten keinen Rückgabewert („undefined" beziehungsweise „{}"), obwohl der darin enthaltene Klick auf „Wiederholen" bereits ausgeführt worden war. Ich hielt sie für fehlgeschlagen und wiederholte sie. Dadurch entstanden zwei zusätzliche Läufe (23:07:18 und 23:07:47), beide erfolgreich.

Die sechs Läufe im Einzelnen: 2 × fehlgeschlagen (Kaltstart), 4 × erfolgreich. Zwei davon waren `analyze` (read-only), vier `edit`. Alle vier Diffs warten unveröffentlicht auf Freigabe; das Repository ist unverändert.

Der Fehler war meiner. Für künftige Läufe ziehe ich daraus: Bei ausbleibendem Rückgabewert erst den Serverzustand prüfen, bevor eine kostenpflichtige Aktion wiederholt wird.

## 11. Verbleibende Risiken

1. **Die Zuverlässigkeit ist nicht belastbar gemessen.** Sechs Läufe sind eine kleine Stichprobe. Ob die Erfolgsquote bei warmem Worker wirklich bei 100 % liegt, müsste über mehrere Tage und aus der Kaltstartsituation heraus geprüft werden.
2. **Der Kaltstart-Zusammenhang ist eine begründete Vermutung, kein Beweis.** Das Muster ist deutlich (2 Fehlschläge, dann 4 Erfolge; historisch 8 Fehlschläge nach langer Pause), aber ich habe die Ursache nicht im Serverlog verifiziert.
3. **Fremde Repositories sind ungeklärt.** Ob ein fremdes Repository bei warmem Worker tatsächlich verarbeitet würde, ist offen.
4. **Der Veröffentlichungspfad ist ungeprüft.** Der Riegel hält — dass er hält, habe ich belegt. Ob eine erteilte Freigabe anschließend korrekt zu einem Draft-PR führt, ist nicht getestet.
5. **LCP und INP fehlen.** Zwei der sechs Performance-Budgets sind mangels Messwerkzeug unbewertet.
